Clear a stuck Xcode test execution slot for this project.

Only one Test Run may hold a project's execution slot at a time. When a previous
run's lifecycle could not be confirmed — the tool crashed, or a process could
not be accounted for — the slot stays held rather than being handed to a new
run, because starting a second xcodebuild while an unaccounted-for one may still
be writing the same build directory produces results nobody can explain.

Call this when xcode_test reports that the execution slot is quarantined. It
takes no arguments: recovery is idempotent, bounded, and always scoped to this
project. It never interrupts a run that is genuinely still active.

Call it too when xcode_test reports that the tool could not start because a
probe did not answer in time and calls that transient. Recovery then probes the
runtime and Xcode toolchain again, once, within the startup budgets; if they
answer, the tool is available from then on. Nothing is retried on its own, and a
failure that is not a timeout (an invalid configured runtime, no Bun, an
unusable Xcode) is reported as such rather than probed again.

It returns one of:

  recovered         work was reconciled and the slot is usable again
  alreadyHealthy    nothing needed doing
  busy              a live run still owns the slot; wait for it
  deferred          another instance is reconciling right now; nothing was
                    examined, so try again in a moment
  stillQuarantined  the previous run's state remains unresolved
  cancelled         recovery was cancelled partway
  failed            recovery could not complete

stillQuarantined is not a reason to retry in a loop. It means a process could
not be accounted for, and the next step is to find out which.
